---
name: plan-task
description: 새 개발 요청을 목표·범위·완료 기준이 있는 작업으로 정리한다. 단순 설명 질문에는 사용하지 않는다.
---

1. `.claude/tasks/index.md`와 `python3 .claude/hooks/workflow.py status`로 기존 작업을 확인한다.
2. 관련 코드·실행 설정·기존 테스트를 읽는다. 선택 이유가 필요하면 `docs/decisions.md`를 읽는다.
3. 사용자 요청을 그대로 구현 명령으로 취급하지 않는다. 먼저 기존 코드·문서에서 확인 가능한 사실과 사용자 의도가 필요한 선택을 분리한다. 행위자, 입력·출력, 정상·실패·경계, 권한, 데이터 보존·동시성, 외부 연동, 성능·운영 조건 중 해당하는 항목을 점검한다. 관련 없는 항목은 질문하지 않는다.
4. `python3 .claude/hooks/workflow.py new <id>`로 작업을 만든다. ID는 소문자·숫자·하이픈이다.
5. 생성된 `task.md`의 요구사항 구체화에 사용자의 원문 요청을 기록한다(첫 줄은 `원문 요청:` 뒤, 길면 이어지는 줄까지). 요청 해석·조사한 사실·중요한 미결정 사항도 적는다. 동작이나 범위가 달라질 선택은 `Q-번호`로 적고 1~3개씩 짧게 질문한다. 각 답변을 `해결` 또는 근거 있는 `범위 제외`로 반영한 뒤 새 모호함이 생겼는지 다시 점검한다. 핵심 질문이 남으면 `wait "사용자 결정 대기: Q-번호"`로 멈추고 구현하지 않는다. 질문이 필요 없다면 기존 근거와 질문하지 않은 이유를 적는다. 임의의 기본값을 사용자 결정으로 기록하지 않는다.
6. [작업 양식](templates/task.md)에 따라 목표·범위와 `REQ-번호`가 붙은 관찰 가능한 요구사항을 작성한다. 각 요구사항은 조건·입력과 기대 동작·실패 조건을 구분한다. 완료 기준·테스트 시나리오가 요구사항을 빠짐없이 검증할 수 있을 때만 `명세 상태: 확정`으로 바꾼다. 클래스·메서드 같은 구현 방법은 요구사항 자체로 쓰지 않는다.
7. 성능 테스트 필요 여부와 이유를 task.md에 기록한다. API·DB 쿼리·동시 처리 등 성능에 영향을 주는 변경은 검토 대상이다. 필요하면 측정 조건·지표·통과 기준을 사용자와 정하고 완료 기준에도 포함한다. 기존 기능 개선은 구현 전에 같은 조건으로 기준 성능을 측정해 결과를 남긴다. 신규 기능은 비교 기준이 없음을 기록한다.
8. docs/testing-policy.md의 영역 선택표와 해당 상세 기준을 읽고 task.md에 적용 여부·기준 ID·명령·기대 결과·시점·증거 위치를 연결한다. verifier를 계획 모드로 호출해 **질문 누락·임의 가정·요구사항 ID와 테스트의 불일치**도 확인받는다. 호출 뒤 `status`의 마지막 계획 호출에 기록된 `plan_snapshot`을 확인하고, 실제 응답을 plan-review.md에 보존하면서 `대상 계획 지문: <64자리 값>`과 `최종 판정: 통과 권고` 또는 `최종 판정: 수정 필요`를 별도 줄에 기록한다. 필수 누락을 해소하고 task.md나 테스트 기준이 바뀌면 verifier를 다시 호출한다. 계획 리뷰는 최초 1회·재리뷰 최대 2회이며 plan-review.md에 회차를 남긴다. 한도 이후 자동 수정은 중단하고 미해결 사항과 선택지를 보고한다. 호출 불가면 block으로 기록하고 미완료로 보고한다.
9. `progress.md`에 다음 행동을 기록한다. 계획만 요청한 경우 여기서 마친다.
10. `start`는 확정 명세·미결정 질문 없음·요구사항 ID와 현재 계획 지문에 대한 verifier 호출 및 명시적 통과 판정, 두 기준 표의 데이터 행을 요구한다. 구현 중 명세를 바꾸면 다시 계획 검증과 start가 필요하다.
11. 구현까지 요청받았으면 `implement-task` 스킬로 이어간다. 이미 허용된 구현을 다시 승인받지 않는다.

동시에 여러 작업을 생성하지 않는다. 진행 중 작업과 새 요청의 관계가 불명확하면 먼저 확인한다.
