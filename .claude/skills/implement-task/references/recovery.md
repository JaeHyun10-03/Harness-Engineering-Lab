# 복구 절차

1. 현재 상태, 요구사항, 진행 기록과 실제 코드를 대조한다. 기록만으로 완료를 추정하지 않는다.
2. 이전 검사가 끝나지 않아 verifying에 남았다면 실행 중인 검사 프로세스부터 확인한다.
3. 실패 로그에서 기존 문제와 이번 변경으로 생긴 문제를 구분한다.
4. 해결 가능한 경우 `start`로 구현 단계에 돌아가 수정하고 검사를 다시 실행한다.
5. 같은 실패가 반복되면 새 근거 없이 같은 수정을 반복하지 말고 원인과 접근 방법을 재검토한다.
6. 사용자 선택을 기다리면 `wait "이유"`, 환경 문제로 진행할 수 없으면 `block "원인과 재개 조건"`을 실행한다.
7. 두 경우 모두 progress.md에 완료한 부분·미완료 부분·재개 조건을 기록하고 사용자에게 알린다.

검사 로그에는 명령 출력이 남는다. 비밀값을 출력하는 명령은 사용하지 않는다.
상태나 증거 JSON이 손상되면 임의로 통과 기록을 만들지 말고 원인을 보고한다.

## 상황별 처리

| 상황 | 처리 |
| --- | --- |
| 사용자 선택 필요 | 장단점 설명 → 이유·다음 행동 기록 → wait → 질문 |
| 환경 문제 | 원인·재개 조건 기록 → block → 미완료 보고 |
| 테스트 실패 | evidence/check-*.log 확인 → 남은 리뷰 회차 확인 → 수정·verify |
| 리뷰 결함 | review fail → 남은 회차가 있을 때 수정·테스트·재리뷰 |
| 리뷰 한도 도달 | 자동 수정 중단 → 남은 문제·영향·수정 내역·미해결 이유·선택지 보고 |
| 중단 후 재개 | status·작업 문서·실제 코드 대조 → 한도 내에서 필요한 단계 진행 |

리뷰 한도는 최초 1회 + 재리뷰 2회다. 한도에 도달한 작업은 start로 우회하지 않는다.
사용자가 추가 리뷰를 명시적으로 허용한 경우에만 메인이 review-extend로 1회를 추가한다.
자세한 기준은 [리뷰 반복 제한](../../../../docs/testing-policy.md#리뷰-반복-제한)을 따른다.
작업 방식 변경 이유는 docs/decisions.md, 실험 결과는 docs/experiments/에 남긴다(프로젝트 루트 기준).
