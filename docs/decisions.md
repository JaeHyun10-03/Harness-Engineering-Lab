- 최초 리뷰 1회 + 재리뷰 2회. 선택적 개선은 완료를 막지 않습니다.

- 사용자 허락 후에만 1회씩 연장하며 회차와 보고서를 보존합니다. 계획 리뷰 한도는 지침으로 적용합니다.

## 2026-09-22: 하네스 강화 — 지침을 프로그램 강제로 전환

- 배경: 평가에서 verify 없이 위조한 증거로 complete 통과, .claude 설정 무방비, Bash 무통제, done 이후 Stop 반복 차단, 상태 손상 시 교착을 실증.
- 사용자 선택: 하네스 핵심 파일은 완전 잠금 대신 단계 게이트(implementing에서만 수정). Bash는 파괴적 git·삭제 명령만 차단하고 일반 커밋은 허용.
- 편집 게이트는 허용 목록 방식으로 전환. 증거·상태 파일은 permissions.deny와 Hook으로 이중 거부.
- verifier 호출을 Agent Hook이 기록하고 review·start가 기록을 요구. 기록은 호출 시도만 증명함을 명시.
- Stop은 done을 통과시킨다. 완료 후 변경은 다음 작업의 지문이 잡는다.
- 설명서 그림은 docs/assets로 이동. 리뷰 반복 제한 본문은 testing-policy.md 한 곳에 둔다.

## 2026-09-22: 완료 판정과 검사 이력 보강

- 계획 verifier 호출 시 task.md와 테스트 기준 문서의 지문을 기록한다. 최초 start는 같은 지문에 대한 호출과 plan-review.md의 명시적 `최종 판정: 통과 권고`가 있어야 허용한다.
- 검사 지문에 docs/를 포함한다. Git 저장소에서는 추적 파일과 무시하지 않는 새 파일을 사용하고, 무시된 검사 입력은 snapshot.json의 extra_files에 지정한다. docs/experiments와 작업 기록은 실행 중 작성되는 결과물이므로 제외한다.
- verify 실행마다 별도 verify-NNN 디렉터리에 결과·로그·변경 목록을 보존한다. 최신 checks.json과 changes.txt는 편의를 위한 사본이다. 첫 실패 뒤의 검사는 미실행으로 남긴다.
- 새 작업을 만들 때 Git HEAD와 시작 시 변경 상태를 저장하고, 리뷰 변경 목록에 시작 커밋 이후의 커밋된 변경도 포함한다. 시작 시 이미 변경된 파일은 별도 표시한다.
- 하네스 회귀 테스트를 GitHub Actions에서 독립 실행한다. 실제 앱의 검사와 보호 브랜치 필수 체크는 이식 시 설정한다.

## 2026-09-22: 범용 실행 핵심과 프로젝트 운영 규칙 분리

- 여러 프로젝트에 적용할 수 있는 개발·검증 흐름을 고려하여, 범용 하네스의 중심은 작업별 상태 전환·검사 증거·최신 변경 확인·완료 판정으로 유지하기로 한다. 이 부분은 프로젝트마다 다시 만들지 않는다.
- 실제 프로젝트에 이식할 때 도메인 정책, 코드·테스트 규칙, GitHub 이슈·브랜치·PR 절차, 성능 측정, 마이그레이션 보호, CI·배포 조건을 프로젝트 전용 계층으로 연결한다. 필요한 항목만 추가하고 기존 설정과 충돌하지 않게 합친다.
- 정보의 원본을 나눈다. GitHub 이슈는 팀이 합의한 목표와 이유, 하네스 작업은 진행 상태와 실행·검증 증거, PR은 변경 내용과 팀 리뷰를 담당한다. 같은 요구사항이나 판정을 여러 곳에 독립적으로 복사해 관리하지 않는다.
- 이식 완료 조건은 실제 프로젝트 검사 명령과 필수 CI 체크를 연결하고, 샘플 작업에서 실패 차단·재검사·리뷰·재개가 동작하는지 확인하는 것이다. 현재 실험용 하네스에는 프로젝트 전용 규칙을 미리 고정하지 않는다.

## 2026-09-22: 요구사항 구체화와 명세 대조 게이트

- 새 개발 작업에서는 먼저 기존 코드·문서로 확인할 수 있는 사실과 사용자가 결정해야 할 제품 동작을 분리한다. 중요한 모호함은 1~3개씩 질문하고 답변을 `task.md`에 기록한다. 답변으로 새 질문이 생기면 다시 구체화한다.
- `task.md`에 원문 요청, 요청 해석, 조사한 사실, 질문·결정 기록, `REQ-번호`별 조건과 기대 동작을 둔다. 질문이 없으면 이유를 적는다. 미결정 질문이 없고 요구사항을 검증 가능하게 쓴 뒤 명세를 확정한다.
- 새 작업의 start는 확정 명세와 계획 verifier 판정을 요구한다. 구현 중 명세·테스트 기준이 바뀌면 계획 검증과 start를 다시 거쳐야 Edit·Write·NotebookEdit을 통한 코드 편집과 verify를 실행할 수 있다.
- 결과 리뷰는 모든 `REQ-번호`를 구현 위치·테스트·실행 증거에 연결해야 통과 등록이 가능하다. 프로그램은 형식과 누락을 확인하고, 질문의 충분함과 증거의 타당성은 verifier가 원문을 읽어 판단한다.
- 기존 완료 작업의 기록은 새 형식으로 소급 변경하지 않는다. 이 방식은 명세 기반 개발의 구체화·추적 단계이며, 프로젝트별 설계 문서와 구현 작업 분해는 실제 프로젝트에 맞춰 추가한다.

## 2026-09-23: 범용 설정·안전한 이식·행동 평가 도입

- 하네스 코어에서 기술 스택을 분리하고 `harness.json`과 JSON 프로필로 프로젝트 경로·검사를 선택한다.

- 고정 시나리오와 정규화된 행동 이벤트로 결정 회수율, 질문 효율, 조기 구현, 요구사항 추적, 검사 실행, 허위 완료를 반복 측정한다.
- 모델 실행과 로그 정규화는 어댑터 경계로 분리한다. 현재 평가는 기록된 이벤트를 결정론적으로 채점하며 실제 Claude 실행 자동화는 후속 어댑터 작업이다.
