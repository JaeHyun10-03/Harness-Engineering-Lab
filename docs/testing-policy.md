# 테스트 기준

## 계획에서 정할 것

완료 기준마다 정상·실패·경계값·권한·동시 요청 중 필요한 시나리오와 실행 명령을 연결합니다.
해당하지 않는 항목은 이유를 기록합니다. 필수 테스트를 실행하지 못한 것은 생략이 아니라 미완료입니다.
새 작업은 요구사항에 `REQ-번호`를 붙이고, 각 ID가 적어도 하나의 완료 기준과 테스트 시나리오에 연결되는지 확인합니다.

## 영역별 상세 기준

| 영역 | 읽는 조건 | 상세 문서 |
| --- | --- | --- |
| 프론트 | 화면·입력·상태·브라우저 변경 | [frontend.md](testing/frontend.md) |
| 백엔드·데이터 | API·업무 로직·DB·캐시·메시지 변경 | [backend.md](testing/backend.md) |
| AI | 제품에 LLM·RAG·도구 실행·멀티에이전트가 있음 | [ai.md](testing/ai.md) |
| DevOps | 빌드·CI/CD·인프라·배포·복구 변경 | [devops.md](testing/devops.md) |
| 보안 | 권한·외부 입력·비밀·의존성 등 관련 변경 | [security.md](testing/security.md) |
| 성능 | 처리량·지연·자원·동시 처리에 영향 | [performance.md](testing/performance.md) |
| 전체 흐름 | 사용자 기능·영역 간 연결·회귀 | [e2e.md](testing/e2e.md) |

계획에서 모든 영역의 적용 여부를 먼저 판단하고, 적용한 영역의 상세 문서만 읽습니다.
상세 항목 ID마다 적용 또는 해당 없음과 이유를 기록합니다. 없는 기능을 만들 필요는 없지만, 이미 있는 기능을 편의상 생략하지 않습니다.
AI 문서는 제품 기능 기준입니다. 개발에 AI를 쓴다는 이유만으로 제품 AI 평가를 요구하지 않습니다.

## 기준을 작업에 연결하는 방법

1. task.md에 영역별 적용 여부·이유를 적습니다.
2. 적용 기준 ID → 완료 기준 → 사례·기대 결과 → 실행 명령 → 통과 기준 → 실행 시점 → 증거 위치를 연결합니다.
3. 환경·목표 수치·도구가 미정이면 구현 전 정합니다. 문서의 권고값을 임의로 프로젝트 목표로 확정하지 않습니다.
4. 계획을 verifier에게 검증받고, 구현 후 최신 코드·테스트 증거로 결과 리뷰를 다시 요청합니다.
5. 필수 항목의 실패·미실행·근거 부족 또는 미해결 차단/중요 지적이 있으면 완료하지 않습니다. 적용 제외는 이유를 남기고 verifier가 확인합니다.

실행 기록에는 작업/사례 ID, 코드 식별값, 도구·환경 버전, 시각, 명령, 실제 결과, 기대값, 로그 위치를 남깁니다.
요약 통과율만 적지 말고 실패·재시도 이력과 실행하지 못한 항목도 보존합니다.
분야별 목록은 프로젝트 기본 기준이며 외부 표준 전체 준수 인증은 아닙니다. 도메인별 추가 요구사항은 task.md에 보완합니다.

## 언제 실행하는가

| 시점 | 실행 범위 |
| --- | --- |
| 개발 중 | 변경한 기능의 빠른 테스트 |
| 작업 완료·병합 전 | 앱의 필수 일반 테스트, 해당 DB·API 통합 테스트, 핵심 사용자 흐름 |
| 성능 관련 변경 | 일반 테스트 통과 후 동일 조건의 변경 전후 비교 |
| 배포 전 | 배포 환경에 가까운 곳에서 전체 흐름·호환성·목표 부하 확인 |
| 정기 점검 | 장시간 부하, 급증·장애·복구, 보안 테스트 |
| 배포 직후 | 핵심 기능과 실제 오류·성능 지표 확인 |

작업 완료와 배포 승인은 별개입니다. 해당 작업에 필수인 항목과 후속 배포 점검을 계획에 구분합니다.
현재 하네스는 작업 완료만 제어합니다. CI 병합·배포 차단과 정기 실행은 아직 연결하지 않았습니다.

## 지표와 판정

- 기능: 필수 시나리오 모두 통과. 데이터 중복·유실·권한 위반은 해당 테스트에서 0건.
- 프론트 성능: LCP·INP·CLS, 페이지 전송량, 주요 사용자 흐름 성공 여부.
- 백엔드 성능: API별 p95·p99, 목표 처리량, 예상하지 못한 오류·타임아웃, CPU·메모리·GC, 쿼리·락 대기·커넥션 고갈.
- 성능 조건: 환경·데이터량·부하·시간·반복 횟수·목표를 계획에 기록. 숫자는 임의로 확정하지 않음.
- 재시도: 처음의 실패와 원인을 보존. 재시도 성공만으로 불안정한 테스트를 숨기지 않음.
- 커버리지: 빠진 검증을 찾는 보조 지표. 수치만으로 완료 판정하지 않음.

웹 성능 참고치는 LCP 2.5초 이하, INP 200ms 이하, CLS 0.1 이하입니다.
이는 모바일·데스크톱별 실제 방문의 75번째 백분위 기준이며 로컬 1회 측정으로 충족을 입증하지 못합니다.
일반 Lighthouse 로딩 테스트는 INP를 직접 측정하지 않습니다.

## 실행과 에이전트의 역할

테스트 실행·통과 판정은 테스트 도구와 종료 코드가 담당합니다. 에이전트는 시나리오 설계·테스트 작성·실패 분석·리뷰를 담당합니다.
메인은 계획·구현·테스트 실행·상태 변경을 담당합니다. verifier는 계획의 누락과 구현 후 증거를 읽기 전용으로 검증합니다.
메인은 실제 반환 내용을 계획 리뷰는 plan-review.md, 결과 리뷰는 review.md에 보존하고 각 지적의 처리 근거를 덧붙입니다. 수정 후 최신 결과로 재검증합니다.
verifier 호출 실패·미실행을 자체 리뷰로 대체해 독립 검증 완료라고 기록하지 않습니다. 호출 불가 시 미완료로 보고합니다.
현재 Python은 호출 진위나 기준 ID의 충족 여부를 자동 증명하지 않습니다. 독립 검증 요구는 지침으로 적용하며, 기존 테스트·리뷰 증거 검사는 프로그램이 수행합니다.
verify를 여러 주체가 동시에 실행하거나 같은 작업 상태·증거 파일을 함께 수정하는 구조는 지원하지 않습니다.
성능 측정 중 다른 테스트를 같은 장비에서 병렬 실행하면 측정에 간섭하므로 별도 환경 또는 시간 분리가 필요합니다.

## 리뷰 반복 제한

- 결과 리뷰는 작업당 최초 1회 + 재리뷰 최대 2회다. verifier 호출 직전에 메인이 review-begin을 실행한다. 호출 실패·중단도 시작한 회차를 소비한다.
- 취향·스타일·선택적 개선은 제안으로 기록하며 완료를 막지 않는다. 차단/중요 판정에는 합의한 기준 위반 또는 실제 결함의 근거·영향이 필요하다.
- 해결한 지적은 새로운 근거 없이 반복하지 않는다. 재리뷰는 이전 지적의 해결과 수정으로 생긴 회귀를 중심으로 하되 새로 발견한 실제 결함은 보고한다.
- 메인과 verifier의 이견은 기준·근거로 비교한다. 해소되지 않으면 사용자에게 선택을 요청하며 임의로 통과 처리하지 않는다.
- 세 번째 결과 리뷰가 실패하면 프로그램은 waiting으로 전환한다. start·verify로 자동 수정을 이어가거나 새 작업으로 같은 한도를 우회하지 않는다.
- 남은 문제·영향·수정 내역·미해결 이유와 추가 수정/범위 조정/보류 선택지를 사용자에게 보고한다. 한도 종료는 통과가 아니다.
- 사용자가 명시적으로 추가 리뷰를 허용한 경우에만 review-extend 명령에 결정 내용을 남긴다. 한 번에 1회 추가하며 기존 횟수·보고서를 유지한다. 범위 조정도 추가 작업 허용을 명확히 한 뒤 요구사항 수정·재테스트한다.
- 계획 리뷰도 최초 1회 + 재리뷰 2회로 제한하고 plan-review.md에 회차를 기록한다. 이 계획 리뷰 한도는 지침으로 적용한다.
- 프로그램은 등록된 결과 리뷰 회차를 제한한다. 실제 verifier 호출 횟수나 사용자 허락의 진위는 자동 증명하지 못한다.
